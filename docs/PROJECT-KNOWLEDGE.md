## TJ filter chain (`packages/crawler/src/adapters/tj-media-direct/filterSteps.ts`)

A 7-step reducer drives `classifyRecord` in `parser.ts`. The `FILTER_STEPS`
array in `filterSteps.ts` is the ONE authoritative statement of the order,
and **the order is load-bearing — do not reorder**:

1. `reviewed-song-drop` — hand-audited TJ-number false positives
   (`reviewedSongOverrides.ts` DROP list) stay out even against stale caches
   or blog rescue.
2. `non-jpn-pro-reject` — an explicit non-JPN `nationalcode` from enrichment
   overrides EVERY admit path, including reviewed-song-allow.
3. `reviewed-song-allow` — hand-audited TJ-number admits (ALLOW list).
   **Owner policy:** K-pop/Korean-artist Japanese releases are admitted ONLY
   by exact TJ number, never artist-wide.
4. `drop-list-reject` — Korean/Chinese artist deny lists, matched against any
   collab component. Strongest negative signal after step 2; **must precede
   `jpn-admit-pro`** — otherwise a drop-listed Korean act carrying a JPN pro
   tag (and not in the ALLOW list) would leak into the corpus. Owner policy:
   drop-list wins; genuine K-pop Japanese releases go in the ALLOW list by
   exact TJ number.
5. `jpn-admit-pro` — per-song JPN `nationalcode` (strongest positive signal).
6. `jpn-admit-artist` — lead-component-only artist JPN tag (the primary
   confirmation path by volume). **Its admit branch carries two script
   vetoes** (both return `pass` → fall-through, added 2026-07-13): a
   Korean-script veto (Hangul AND no Japanese over `title + artist`,
   PR #143 — LOCAL regex constants deliberately byte-mirroring the #97
   leakage gate, NOT the broader shared `hasHangul` which also matches
   jamo) and a simplified-Chinese veto (`hasSimplifiedOnlyHan` from
   `@karaoke/search`, PR #148 — deliberately single-sourced with the
   report-only audit). Rationale: the per-song KOR signal is LAGGING (the
   translit pass writes it post-classify), so a newly-surfaced Korean row
   would otherwise leak for exactly one crawl before self-healing;
   Latin/romaji-titled Korean rows carry no script signal, so the curated
   drop lists remain load-bearing for that tail.
7. `blog-rescue` — safety net for TJ-search index gaps. NOT dead code.

Related machinery:

- `reviewedSongOverrides.ts` is TS-only (no JSON sidecar, no Python
  consumer), keyed by leading-zero-normalized TJ number, with structured
  per-entry metadata. Admits emit `via: 'song-override'`.
- `GENERIC_ARTIST_JPN_ADMIT_BLOCKLIST` (`filterSteps.ts`): generic bucket names
  (`variousartists`, `オムニバス`, …) must never blanket-admit on a JPN
  artist tag, and `blog-rescue` refuses to rescue a generic lead component.
- Per-record enrichment uses `searchSongByPro` (exact TJ-number lookup,
  `strType=16` + `strWord='Y'`, client-side exact `pro` match to reject
  neighbor numbers) — not title search. It records the TRUE `nationalcode`
  (incl. KOR/ENG), which feeds `non-jpn-pro-reject`.
- `verdictFromVotes` requires JPN ≥ 3 AND JPN/(JPN+KOR) ≥ 0.7 (symmetric for
  KOR). It works because `bootstrapCharts.ts` sources both JPN votes (JPOP
  chart sweep) and KOR votes (KPOP chart sweep).

## Drop lists, splitter, and sidecar/parity machinery

- Korean drop list: `koreanArtistDropList.ts` (structured
  `DropListEntry { canonical, variants, lastReviewed }`). Its JSON sidecar
  `korean-artist-drop-list.json` is auto-regenerated by
  `scripts/export-drop-list.mjs` on crawler build and is **kept because
  `scripts/ingest_anisong_pdf.py` (Python) still consumes it**. CI fails on
  sidecar drift (byte-compare after build) in both `ci.yml` and `crawl.yml`.
- Chinese drop list: `chineseArtistDropList.ts`, a flat `string[]`
  (schema asymmetry vs Korean is deliberate at its current size; align if it
  grows past ~20). Its former JSON-sidecar/Python machinery was deleted —
  corpus-level cleanup now goes through `scripts/drop-artist-leaks.mjs`
  (`--list korean|chinese`), which imports the canonical predicates straight
  from the built crawler dist, so crawl-time and corpus-level filtering are
  the same predicate by construction. The chinese pass also drops a small
  hardcoded catalog-anomaly ID list (records whose artist field itself is
  malformed, e.g. `tj-72638`).
- `splitArtistCollab` (`packages/crawler/src/clustering.ts`): the ` of `
  member-of-group sub-split fires ONLY inside `(Feat.X)` / `(Prod.X)`
  parentheticals — bare ` of ` never splits (protects BUMP OF CHICKEN).
  `SPLIT_RE_SOURCE` must keep `\s+meets\s+` and the full-width pipe `｜` in
  the delimiter set; both have regression tests
  (`scripts/test_splitter_parity.py` on the Python side). The TS source is
  exported to `packages/crawler/src/clustering-rules.json` at build time so
  Python consumes the sidecar instead of hand-mirroring the regex.
- **Pinned limitation** (documented in
  `packages/crawler/test/clustering.test.ts`): `A(Feat.X)B` with NO delimiter
  around the parenthetical yields a glued `A B` component, not separate
  `A` + `B`. Unobserved in the live corpus; a fix in `splitArtistCollab`
  heals both the parser and `drop-artist-leaks.mjs` at once.

## Merger and alias resolution (`packages/crawler/src/merge.ts`, `aliases.ts`)

- Three tiers: **A** — per-vendor union-find on shared `karaoke_numbers`;
  **B** — normalized `(title_primary, artist_primary)` key; **C** —
  primary-token key, **cross-source only** (same-source clusters never merge
  via Tier C — this kills original-vs-remix false positives that share
  primary tokens).
- Per-field ownership: TJ wins title/artist; blog wins Korean fields; vendor
  numbers union with `blog > tj > tjpdf > joysound` tiebreak.
- `mergeRecords` returns `MergeResult { records, conflicts }` — destructure
  at every call site. Tier C merges are recorded as `tier_c_merge` entries
  but excluded from the headline conflict count (they are merges, not
  disagreements).
- Artist-alias resolution runs BEFORE `mergeRecords`. It splits
  `artist_primary` on **full-width pipe `｜` (U+FF5C) only — never ASCII
  `|`** (ASCII pipe is preserved for band names like `Qverktett:||`). First
  segment becomes canonical, the rest become `artist_aliases`; bare records
  whose `artist_primary` matches a known alias are re-keyed to the canonical.
  Alias collisions (one alias → two canonicals) leave both records untouched
  + warn — never auto-merge across distinct artists. After this resolver,
  Tier B/C cluster naturally on canonical `artist_primary`.

## Schema (`packages/schema/src/index.ts`)

- Cross-field Ajv `allOf if/then` constraint: `title_ko_confidence` is only
  valid when `title_ko_source === 'llm-translated'` — e.g. a blog record
  carrying a confidence tag is schema-invalid.
- `karaoke_numbers.joysound` carries `pattern: '^[0-9]+$'` (dashless).
- Runtime imports need `pnpm -r build` first — `@karaoke/schema` exports
  `dist/index.js`, not `src/index.ts`.
- **The committed corpus is schema-validated on every PR**, not just during
  crawls: `ci.yml`'s `sqlite:build` step imports the committed corpus through
  `@karaoke/data-store`'s `importSongsJson`, which calls `validateSongRecord`
  on each committed record (plus duplicate-id detection) while building the
  self-host SQLite database. Consequence: tightening a schema constraint
  fails PR CI immediately unless the committed corpus already satisfies it —
  you cannot defer enforcement "until the next crawl". Either clean the
  offending committed records in the same PR or land the constraint with a
  regenerated corpus.

## title_ko backfill pipeline

Three optional `SongRecord` fields: `media_context_ko` (Korean rendering of
an anime/OST/OP/ED parenthetical), `title_ko_source`
(`'blog' | 'llm-translated' | 'manual'`), `title_ko_confidence`
(`'high' | 'medium' | 'low'`, llm-translated only — see the schema constraint
above).

- **Stage 1** (`scripts/normalize_tj_title_ko.py`): strips TJ-derived
  katakana→Hangul transliteration `title_ko` from `tj-`/`tjpdf-` records
  (TJ's `sortTitleKo` is a catalog sort helper, not a translation), salvages
  Korean media-context parens into `media_context_ko`, tags blog records
  `title_ko_source = 'blog'`. Idempotent. CRITICAL guard: the TJ branch
  short-circuits when `title_ko_source === 'llm-translated'` already exists —
  without it, re-running Stage 1 would nuke the agent translations.
- **Stage 2** (`scripts/translate_title_ko_via_agents.mjs prep|merge`):
  `prep` chunks eligible records into
  `scripts/data/llm-translations-chunk-NN-input.json`; an operator dispatches
  one LLM agent per chunk (worker prompt:
  `scripts/title_ko_stage2_worker_prompt.md`; operator guide:
  `scripts/title_ko_stage2_howto.md`); `merge` applies the chunk outputs and
  (with `--review-csv`) writes the medium/low-confidence review CSV **with a
  UTF-8 BOM** (Korean Excel defaults to CP949 without it → mojibake).
  `filterTranslatableRecords` skips records that already have a
  `title_ko_source` or whose title is pure-Latin, so re-runs only pick up
  newly-crawled records.
- **Cache replay**: the chunk OUTPUT files
  (`scripts/data/llm-translations-chunk-NN.json`) are tracked in git as the
  source-of-truth translation cache; the post-crawl pipeline re-applies them
  on every weekly crawl. `applyDecisionsToCorpus` gates on
  `id + title_primary` match — a TJ title edit invalidates the cached
  translation and the record passes through untouched.
- **Manual fixes sidecar** (`scripts/data/title-ko-manual-fixes.json` +
  `scripts/apply-manual-title-ko-fixes.mjs`): tracked JSON array of
  `{id, title_primary, title_ko}`. Replayed by the pipeline AFTER the Stage 2
  replay, and hard-fails (explicit user corrections gate the crawl, unlike
  the continue-on-error Stage 2 replay). It NFKC-compares `title_primary` to
  guard against stale fixes after a TJ title edit (a mismatched entry is
  skipped, not applied). Applied records get `title_ko_source: 'manual'` and
  DROP `title_ko_confidence`. Adding a fix = edit the sidecar JSON, commit;
  the next pipeline run applies it.
- **Pitfall (2026-07-10, caught in PR #122 review; generalized in PR #125):
  any change that edits a record's `title_primary` (ingest overrides, parser
  fixes, source swaps) silently disarms that record's title_ko on TWO guard
  surfaces** — (1) the manual-fixes sidecar (NFKC guard mismatch → skip with
  exit 0 + stderr counter → an owner-signed correction quietly reverts) and
  (2) the Stage-2 replay cache (`translate_title_ko_via_agents.mjs` looks up
  by id but APPLIES only when the cached `title_primary` NFKC-matches → the
  cached translation silently stops re-applying). RULE: whenever
  `title_primary` changes for an id present in `title-ko-manual-fixes.json`
  OR the `llm-translations-chunk-*.json` cache, realign BOTH stored
  `title_primary` guards in the SAME change (translations byte-preserved),
  and pin the alignment with tests (patterns: PR #122's manual-fix guard
  test; PR #125's catalog↔manual-fix and catalog↔cache drift pins).

## HTTP client (`packages/crawler/src/http.ts`)

- Default rate limit 200 ms + 50 ms jitter; per-host overrides in
  `HOST_CONFIG` (`www.tjmedia.com` → 500 ms + 100 ms). Per-host `cache`
  opt-out exists; opting out does NOT prune already-cached entries from
  `.cache/http.json`.
- Cache persists are **batched** (default: every 200 stores or 30 s,
  whichever first, plus a final `flush()`): persisting rewrites the entire
  cache file atomically, so persist-per-store is O(n²) IO over a long crawl.
  A crash loses at most the last un-flushed batch — acceptable for a cache.
- The response cache is **unbounded**: every 2xx body is held in one in-memory
  object and the WHOLE object is re-serialized to `.cache/http.json` on each
  persist. A bulk enumeration crossed V8's max string length at ~1.1k large RSC
  pages (`RangeError: Invalid string length` in `JSON.stringify`, 2026-07-10,
  JOYSOUND fullCatalog listing). **Rule:** any one-shot bulk enumeration of
  >~1k large pages must construct the client with `new HttpClient({ cache:
  'off' })` — it never refetches a URL in-run, so the cache buys nothing and is
  pure liability. The weekly-crawl lane leaves the default `'persistent'` mode.
- `searchSong` strips ASCII apostrophes from `searchTxt` to work around a TJ
  server parser bug (`resultCode=04`). Escaping (`\'`, `%27`, …) hits the
  same bug — don't try.
- TJ search cache schema: `{ version, generatedAt, proEnrichmentMap,
  artistNationalityMap }` with a forward-compat `extras` bag that round-trips
  unrecognized top-level fields.

## Data-script conventions

- All Python and JS data scripts write atomically (`<file>.tmp` then rename).
  Re-running on unchanged input is byte-idempotent. Canonical corpus byte
  shape: JSON `indent=2` + trailing newline (Python helper
  `scripts/lib/corpus_io.py:atomic_write_corpus`, JS
  `scripts/lib/corpus.mjs` / `scripts/lib/atomic-write.mjs`).
- `scripts/run-post-crawl-pipeline.mjs` owns the `KARAOKE_SONGS_JSON` env var
  for its child steps: set (absolute) when `--corpus` is given, deleted
  otherwise. Caveat: the cache-prune step always mutates the real
  `tj-search-cache.json` regardless of `--corpus`.
- `scripts/ingest_anisong_pdf.py` reads the cached text
  `scripts/data/anisong_utf8.txt` (tracked). Regenerating it from a new
  source PDF requires xpdf's `pdftotext -table` (ships with Git for Windows;
  Linux poppler-utils does NOT support `-table`).
- Crawler CLI `--limit N` caps **artist pages per adapter**, not output
  records. A full crawl is hours of wall time (network-bound, per-record TJ
  enrichment); for smoke tests prefer `--limit 5` or CI `workflow_dispatch`.

## Search DB: delta patch and query expansion

- `createSongDatabase` converges a legacy DB to the canonical schema, which for
  a fully-derived table it can't ALTER in place (drop `search_texts.text_norm`,
  widen a `field`/`kind` CHECK) means DROP+recreate — a WHOLE-TABLE operation
  that empties that table for EVERY song. The delta patcher calls
  `createSongDatabase` and used to then re-derive only the touched songs, so on
  a pre-#93-shaped served DB (the live v21 case) every UNTOUCHED song silently
  lost its `search_texts` rows (the exact-text serve tier) while docstrings
  claimed the tables were "cleared per-song by the delta patcher". Rule: a
  migration that drops a derived table inside the delta path MUST trigger full
  re-derivation of ALL songs (now implemented — `createSongDatabase` returns a
  `SongDatabaseMigrationReport`, and the patcher falls back to a whole-corpus
  rebuild + full stat recompute + full hint materialization; regression-tested
  in `packages/data-store/test/delta-legacy-migration.test.ts`). Never document
  per-song safety for a whole-table operation.
- `expandSearchQuery` (`@karaoke/search`) feeds user query text to wanakana
  (`toHiragana`/`toKatakana`/`toRomaji`), which parses by per-token recursion
  and overflows the call stack near ~5-6k ASCII chars; unbounded `q` surfaced as
  `/api/search` HTTP 500s. Rule: bound query length at the API edge (the worker
  rejects `q` over 256 code points with a 400) AND guard expansion length inside
  `@karaoke/search` (`MAX_EXPANDABLE_QUERY_CODE_POINTS`, returns the query
  unchanged above the bound). Never feed unbounded user text to wanakana.

## Frontend / UI invariants

- Playwright e2e must use `await page.goto('')` (relative empty string).
  `goto('/')` resolves against the configured base URL's origin and sends the
  test to the bare domain root. Keep the relative-empty form so the same spec
  works for root deployments and any future non-root preview base.
- `apps/web/src/styles/global.css` was hoisted verbatim from
  `index.astro`'s `<style is:global>` — **rule order is load-bearing; do not
  reorder or split** (pinned in the file's first line).
- `--header-height` token (`apps/web/src/styles/tokens.css`) must match the
  actual rendered header: editing `.site-header` padding or
  title/subtitle typography requires re-deriving the value (formula pinned
  in a comment next to the token) or the sticky tab bar leaves a visible
  stripe at scroll. A `ResizeObserver` migration is a pinned TODO.
- Mobile `.tab-bar` edge-bleed needs BOTH `width: calc(100% + …)` AND
  negative `margin-inline`; `--rui-pill-secondary-bg` (light `#dfdfe2`) must
  stay visually distinct from both `--rui-surface` and `--rui-surface-hover`;
  mobile chip sizing intentionally diverges from DESIGN.md; horizontal chip
  rows hide their scrollbars deliberately. These are documented UX decisions
  — don't "fix" them without sign-off (details in comments in `tokens.css` /
  `global.css`).
- Tab switch in `App.tsx` deliberately resets ephemeral filter state (input,
  query, vendor chips) and cancels the pending search debounce; favorites
  (localStorage `karaoke-favorites:v1`) persist. The render branch is a typed
  `RenderMode` discriminator with an exhaustive `default: never` arm — adding
  a mode without a case fails typecheck.

## Self-host service permissions (intentional — do not tighten)

The hermes-host self-host deployment intentionally runs permissive while it
is under active development, so the operator can write anywhere in the tree
without friction:

- `karaoke-api.service` sets `ReadWritePaths=/srv/karaoke` (the whole tree,
  not just `db/current`).
- `karaoke-api.env` and `tailscale-cert/` sit as plain files in the NAS tree
  root (`/nas/karaoke`, also exposed over SMB), and `migration-backups/`
  keeps a pre-migration copy of the env file.

This is a deliberate owner decision (recorded 2026-07-02), **not** an
oversight. Do not tighten the unit sandboxing, chmod/move the env or cert
files, or delete the backup copy without explicit owner sign-off. Revisit
once the self-host setup stabilizes.

## Windows development notes

- Always `corepack pnpm` — plain `pnpm` may not be on PATH.
- `songs.json` may show a perpetual CRLF-related modified stat flag with zero

## CI, test gates, and record identity (2026-07-09/10 incident lessons)

- `pnpm -r test` (pnpm recursive run) BAILS at the first failing package, so
  every later package silently never runs — after #95 the crawler corpus
  regression masked 14 apps/web parity failures for days, and a "one failure"
  summary was really "one failure plus everything behind it unexecuted". Rule:
  any full-workspace test verdict must use `pnpm -r --no-bail test` (or
  per-package runs) and cite per-package summaries; a bailed run proves only
  the packages that actually executed.
- PRs opened with the default `GITHUB_TOKEN` (e.g. by
  peter-evans/create-pull-request in `crawl.yml`) do NOT trigger
  `on: pull_request` workflows — GitHub suppresses recursive workflow events —
  so `ci.yml` never ran on weekly crawl PRs and #95 merged a regressing corpus
  with green-looking status that only turned red on the post-merge main push.
  Rule: any PR a workflow generates must carry its gates INSIDE the generating
  workflow (the crawl job now runs the crawler corpus-regression suite and the
  parity-baseline regen/delta before opening its PR); never assume repo-level
  CI covers bot-opened PRs.
- `blog-*` record ids WERE POSITIONAL (`blog-{artistId}-{rowIndex}`): any crawl
  that re-touched a blog page reassigned the id→song mapping wholesale (#95
  moved 137/149 ids on the Utada page alone). Anything that pinned a blog id
  across crawls silently re-targeted a different song — this broke the parity
  smoke fixtures and device favorites (localStorage stores record ids). The
  stable-identity design SHIPPED 2026-07-14: blog rows now demote to the lowest
  merge rank (merged clusters take the vendor id) and standalone blog rows mint
  `blog-{artistId}-{vendor}-{number}` from the row's first claimed vendor number
  — stable across crawls. This takes effect in the corpus at crawl resume; the
  frozen v22 serving corpus still carries the old positional ids until then.
  Rule (still holds): never pin a positional `blog-{artistId}-{rowIndex}` id
  across crawls; the stable identity is the vendor karaoke number (tj/ky/joysound),
  which the new minting now encodes directly.
- Re-keying id-keyed SIDECARS (Stage-2 title_ko cache, `search-hints.jsonl`) to
  a FUTURE corpus state must model CRAWL-time semantics, not candidate state.
  The post-crawl sweep's conflict resolution nulls misattributed blog vendor
  cells in the built candidate, so minting residual ids from candidate records
  diverges from what the normalizer mints from the parsed blog rows (the v22
  two-sided replay found 297 such rows + 10 title-merged numberless). Rule:
  derive re-key targets from the parsed source numbers — the authoritative
  old→new map the replay emits — never from post-conflict-resolution candidate
  state.

## Script detection: kana punctuation is not script

Context: title language classification (Stage-2 eligibility, "Latin-only →
title_ko null" decisions, any future script predicate).
Pitfall: the katakana middle dot ・ (U+30FB), its half-width form ･ (U+FF65),
and the sound marks ゛゜ (U+309B/309C) sit INSIDE the kana Unicode blocks but
are punctuation/stylization, not script — romanized titles use ・ as a word
separator ("HI・MI・KO", "Merry・Go・Round"). A naive kana-block regex counts
them as Japanese; the inverse mistake (an ASCII-focused check that ignores
kana entirely) mislabeled 22 genuinely-Japanese titles as "pure Latin" with
an unearned high-confidence null title_ko (recovered 2026-07-13, PR #147).
Rule: script predicates must exclude U+30FB/FF65/309B/309C from "contains
kana/Japanese" decisions, and any "Latin-only" verdict must be computed on
the core title with ALL trailing parenthetical groups removed (depth-counting
— tie-up parens nest, e.g. "…(激闘!クラッシュギアＴ(ターボ) OP)").
